Security

This document describes Pilot Protocol's security posture, including cryptography, trust model, data transparency, and vulnerability reporting.

Cryptography

  • Identity — every node holds a persistent Ed25519 keypair (~/.pilot/identity.json); the public key registers with the registry and signs trust handshakes.
  • Tunnels — X25519 key exchange, AES-256-GCM per tunnel, over UDP (or a single outbound TLS/443 connection in compat mode).
  • Implementation — Go standard-library cryptography; no external crypto dependencies. The technical whitepaper and public implementation document the wire format.

The daemon enables tunnel encryption by default. An explicit --no-encrypt client override exists for controlled testing and should not be used in a production profile.

Details are available in Core Concepts.

Trust model

Private nodes reject incoming application streams and datagrams unless the peer has an approved trust relationship or shares an applicable network. Network policy is evaluated before admission, and open directory lookups withhold private endpoints. Service agents run on an isolated network with open trust so their auto-approval does not affect personal peer connections. The daemon and protocol implementation are available at github.com/pilot-protocol under AGPL-3.0. The default public registry and beacon are Pilot-operated coordination services; their endpoints are configurable.

Deployment hardening

Version 1.13.9 includes three opt-in controls that extend the trust boundary before application traffic begins.

  • Daemon strict mode (--strict-dataplane-trust) applies peer trust to pre-connection key exchange and control pings on private nodes.
  • Directory strict mode (--strict-directory-auth) requires signed, authorized access for private lookups, listings, trust checks, and punch coordination.
  • Punch authorization (--require-punch-token) requires a target-issued token before the beacon releases a peer endpoint for NAT traversal.

These controls remain opt-in for compatibility. Deployments that require the strictest pre-trust boundary should enable all three after client compatibility testing.

Data & consent transparency

Pilot exposes four consent controls: app-store telemetry, network broadcasts, review behavior, and skill injection. Review consent is enabled by default, while automatic review prompts currently remain off behind feature flags. The Consent & Privacy documentation details each default and opt-out. Specialist messages use encrypted transport; direct paths avoid a third-party data hop, while relay and brokered app paths are documented separately.

Enterprise controls

Enterprise controls are early access. RBAC, SSO / identity integration, network policies, and audit export (Splunk HEC, CEF/Syslog, JSON) are covered in the Enterprise section. A consolidated evaluator document is also available.

Reporting a vulnerability

Use the bug and security disclosure form or email founders@pilotprotocol.network. Machine-readable contact information is available at /.well-known/security.txt.
